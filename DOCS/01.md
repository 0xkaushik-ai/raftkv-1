## 1. What is the Raft Algorithm?

Raft is a **consensus algorithm**: it lets a group of servers agree on the same ordered log of commands even when some of them crash or the network drops messages. Diego Ongaro and John Ousterhout published it in 2014 ("In Search of an Understandable Consensus Algorithm"). They designed it to do the same job as Paxos while being much easier to understand and implement.

### The problem it solves
You want a replicated state machine. Several servers (usually 3 or 5) each keep a copy of some state, such as a key-value store. They have to apply the same commands in the same order, so they stay identical and the service keeps running if a minority of them fail.

### Core ideas

**1. Server roles.** Each server is in one of three states:
- **Leader:** handles all client requests and replicates log entries to the others.
- **Follower:** passive; responds to the leader and to candidates.
- **Candidate:** a follower that is trying to become the new leader.

**2. Terms.** Time is split into numbered *terms*. Each term starts with an election and has at most one leader. Term numbers act as a logical clock, so servers can spot stale leaders and messages.

**3. Leader election**
- The leader sends regular **heartbeats** (empty `AppendEntries` RPCs).
- If a follower hears nothing before its **randomized election timeout** (e.g. 150–300 ms), it increments its term, becomes a candidate, votes for itself and sends `RequestVote` RPCs to the others.
- A candidate that gets votes from a **majority** becomes leader.
- The timeouts are randomized so that split votes are rare and get resolved quickly.

**4. Log replication**
- A client sends a command to the leader, which appends it to its log.
- The leader sends the entry to followers with `AppendEntries`.
- Once a **majority** have stored the entry, it is **committed**. The leader applies it to its state machine and replies to the client.
- Followers apply committed entries in the same order.
- Each `AppendEntries` includes the index and term of the previous entry. If a follower's log doesn't match, it rejects the request, and the leader steps back until the logs agree. It then overwrites the follower's conflicting entries.

**5. Safety guarantees**
- **Election restriction:** a server only votes for a candidate whose log is at least as up to date as its own. This means any elected leader already has every committed entry.
- **Log Matching:** if two logs have an entry with the same index and term, the two logs are identical up to that point.
- **Leader Completeness:** once an entry is committed, it appears in the logs of all future leaders.
- **State Machine Safety:** no two servers ever apply different commands at the same log index.

### Fault tolerance
A cluster of **2f + 1** servers survives **f** failures. For example, 5 servers tolerate 2 crashes. Raft handles crash failures, not malicious (Byzantine) ones.

### Extras in the full protocol
- **Log compaction / snapshots**, so logs don't grow forever.
- **Cluster membership changes**, using joint consensus or single-server changes.
- **Client interaction**, such as deduplicating retried requests and doing linearizable reads.

### Used in
etcd (Kubernetes), Consul, CockroachDB, TiKV, HashiCorp Vault, RabbitMQ quorum queues and Kafka KRaft.

## 2. Consensus and Replicated State Machine

### Consensus
**Consensus means a group of computers agreeing on one answer, even if some of them fail.**

Think of 5 friends choosing a restaurant over text messages. Some messages arrive late, and one friend's phone dies. They still need to end up agreeing on the same restaurant, and nobody should later think they picked a different one.

For computers, the "answer" is usually something like: *"What is the next command, and in what order?"*

### Replicated State Machine
Take it word by word:

- **State:** the data a program is holding right now. Example: a bank account balance of ₹500.
- **State machine:** a program that changes its state when it gets commands, and does it the same way every time. Example: "deposit 100" turns ₹500 into ₹600.
- **Replicated:** copied onto several computers.

So a **replicated state machine** is **the same program with the same data running on several computers, all kept identical.**

#### Simple example
Three computers (A, B, C) each hold a copy of your bank balance, ₹500.

All of them receive the same commands in the same order:
1. deposit 100 → ₹600
2. withdraw 50 → ₹550

Now **A, B and C all show ₹550.** If A crashes, B and C still have the right balance, so the system keeps working.

### How they connect
The copies stay identical only if **every computer applies the same commands in the same order.**

Deciding that order is the hard part, and that is where **consensus** comes in. Raft is the method the computers use to agree on that order.

| Term | Simple meaning |
|---|---|
| Consensus | Computers agreeing on the same thing |
| State machine | A program whose data changes in response to commands |
| Replicated state machine | Identical copies of that program on many computers |
| Raft | The rules the computers follow to reach that agreement |

## 3. Log Replication

**Log replication means copying the list of commands from the leader to every other computer, so they all have the same list in the same order.**

### What is a "log" here?
It isn't an error log. In Raft, the **log is a numbered list of commands**, like a diary of everything that should happen:

```
1. deposit 100
2. withdraw 50
3. deposit 20
```

### What is "replication"?
**Replication means making copies.** So log replication means making copies of that list on every computer.

### How it works in Raft
Say we have 3 computers. **A is the leader**, and B and C are followers.

**Step 1:** A client tells the leader to *"deposit 100."*

**Step 2:** The leader writes it into its own log:
```
A: [1. deposit 100]
```

**Step 3:** The leader sends the entry to the followers: *"Please add this to your log."*
```
B: [1. deposit 100]
C: [1. deposit 100]
```

**Step 4:** The followers reply *"Saved it."*

**Step 5:** Once a **majority** (2 of 3, counting the leader) have saved it, the entry is **committed**, meaning it's final and won't be lost.

**Step 6:** Every computer now **applies** the command, so the balance goes ₹500 → ₹600 everywhere.

### Why wait for a majority?
If the leader crashes right afterward, at least one other computer still has the entry. The next leader is guaranteed to have it too, so nothing that was committed gets lost.

### What if a follower falls behind?
Suppose C was offline for a while:
```
A: [1, 2, 3, 4]
B: [1, 2, 3, 4]
C: [1, 2]        ← missing 3 and 4
```
When C comes back, the leader notices the gap and sends it entries 3 and 4. If C has any wrong entries (for example, left over from an old leader), the leader replaces them with its own. In the end every log matches the leader's.

### Simple analogy
Think of a teacher dictating notes to a class:
- The **teacher** is the leader.
- The **students** are the followers.
- The **notebook** is the log.

The teacher reads out each line and the students write it down. Once most students have written a line, it counts as official. A student who was absent copies the missing lines later, so every notebook ends up the same.

## 4. Why Do We Need This in Distributed Systems?

We need it because **computers fail, and we don't want the service or the data to go down with them.** A distributed system spreads work across many computers, and log replication is what keeps all their copies correct and matching.

### The problem with one computer
Say your bank stores everything on **one server**:

- If the server **crashes**, nobody can use the bank.
- If its **disk dies**, the data is gone for good.
- If it has to **restart for an update**, there's downtime.

One computer is a **single point of failure**.

### The fix is more copies
So we keep the data on **several computers**, which gives us:

- **No downtime:** if one dies, the others keep serving.
- **No data loss:** the data still exists on the other machines.

### The new problem: keeping copies the same
Once you have several copies, they can **disagree**:

```
Server A: balance = ₹550
Server B: balance = ₹600   ← missed the "withdraw 50"
Server C: balance = ₹500   ← missed both commands
```

Now nobody knows which balance is right. That's dangerous: money could be spent twice, or orders lost.

Copies end up different because:
- **Messages get lost** or arrive late on the network.
- **Commands arrive in a different order** on different servers.
- **A server crashes** partway through and misses updates.
- **The network splits**, and two groups of servers can't talk to each other.

### Log replication solves this
It guarantees that:
1. **Every server gets the same commands**, so nothing is missed.
2. **They get them in the same order**, so order mismatches can't happen.
3. **A command is final only after a majority has it**, so it survives crashes.
4. **Servers that fall behind catch up** with the missing commands.

The result is that **all servers behave like one reliable computer**, even though some of them may fail.

### Real-world examples
| System | What would go wrong without it |
|---|---|
| **Kubernetes (etcd)** | The cluster would lose track of which apps are running |
| **Banking databases** | Balances would be wrong or money duplicated |
| **Google Docs-like apps** | Users would see different versions of a document |
| **Kafka** | Messages could be lost or arrive out of order |

### In short
- **Why many computers?** So that one failure doesn't break everything.
- **Why log replication?** So those computers always agree on the same data.

Without it, you'd have to choose between **one reliable-but-fragile computer** and **many computers that disagree**. Log replication gives you **many computers that agree.**

## 5. What is a KV Store?

A **KV store (key-value store)** is a very simple kind of database that **saves data as pairs: a key (the name) and a value (the data).** It works like a dictionary: you look up a word (the key) to get its meaning (the value).

### Example
```
Key           →  Value
-----------------------------
"name"        →  "Rahul"
"age"         →  "21"
"city"        →  "Delhi"
"balance"     →  "550"
```

### Basic operations
A KV store usually supports just three commands:

| Command | What it does | Example |
|---|---|---|
| **PUT** (or SET) | Save a value under a key | `PUT city Delhi` |
| **GET** | Read the value for a key | `GET city` → `Delhi` |
| **DELETE** | Remove a key | `DELETE city` |

### Simple analogies
- **Phone contacts:** name (key) → phone number (value)
- **Locker room:** locker number (key) → your stuff inside (value)
- **Python dictionary:** `{"name": "Rahul", "age": 21}`

### Compared with a normal (SQL) database
| SQL database | KV store |
|---|---|
| Tables, rows, columns | Just key → value pairs |
| Complex queries (JOIN, WHERE…) | Only lookups by key |
| More features | Very simple and very fast |

### Real examples
- **Redis:** a very fast in-memory KV store, often used for caching
- **etcd:** a KV store that uses Raft; Kubernetes stores its settings in it
- **Amazon DynamoDB**, **RocksDB**, **Consul**

### How it connects to Raft
A KV store is the **most common example** used to explain and build Raft:

1. A client sends `PUT balance 600` to the **leader**.
2. The leader adds it to its **log**.
3. The command is **replicated** to the followers.
4. Once a majority has it, it is **committed**.
5. Each server **applies** it to its own copy of the KV store.

```
Server A KV: { balance: 600 }
Server B KV: { balance: 600 }
Server C KV: { balance: 600 }
```

So here the KV store is the **state machine** from earlier, and Raft keeps every server's copy of it identical.

A **replicated KV store** is a good first Raft project, and it's also the classic MIT 6.824 (now 6.5840) distributed systems lab.

## 6. KV Store in Raft

**A "KV store in Raft" means a key-value database that runs on several servers and uses Raft to keep every copy identical.**

There are two separate parts working together:

| Part | Job | Simple analogy |
|---|---|---|
| **Raft** | Gets all servers to agree on the same commands in the same order | The **postman** who delivers the same letters, in order, to every house |
| **KV store** | Actually stores the data (`key → value`) | The **house** that reads each letter and acts on it |

Raft **doesn't care what the commands mean**. To Raft, `PUT name Rahul` is just an entry in a list. The **KV store** is what understands the command and saves the data.

### The layers on each server
```
        Client
          │  PUT x 5
          ▼
┌─────────────────────┐
│     KV store        │  ← understands PUT/GET/DELETE, holds the data
├─────────────────────┤
│       Raft          │  ← agrees on the order of commands, replicates the log
└─────────────────────┘
```
Every server (A, B, C) has both layers.

### What happens on `PUT x 5`
1. The client sends `PUT x 5` to the **leader's KV store**.
2. The KV store hands the command to **Raft**: "please get everyone to agree on this."
3. Raft adds it to the **log** and **replicates** it to the followers.
4. Once a majority has it, Raft marks it **committed**.
5. Raft on **every server** passes the committed command up to its own KV store.
6. Each KV store **applies** it: `x = 5`.
7. The leader replies to the client: **OK**.

```
Server A: { x: 5 }
Server B: { x: 5 }
Server C: { x: 5 }
```

### What about GET?
A `GET x` also goes through the **leader**. That way you get the **latest committed value**, not an old one from a follower that's behind.

### Why build it this way?
- **No data loss:** if one server dies, the others still have `x = 5`.
- **No downtime:** if the leader dies, Raft elects a new leader and the KV store keeps working.
- **Always correct:** every copy holds exactly the same data.

### Real-world example
**etcd**, the database inside Kubernetes, works exactly like this: a KV store with Raft underneath.

### Summary
**Raft makes the servers agree, and the KV store saves the data.** Together they behave like one database that doesn't go down or lose data when a server fails.
